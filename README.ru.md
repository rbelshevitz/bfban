# bfban: что это, зачем и какие преимущества

[English](README.md) | [Русский](README.ru.md)

## Что это

`bfban` — программа для Linux, которая применяет динамический список
заблокированных IP-адресов. Она использует наборы `bpfilter`/eBPF и
интегрируется с Fail2ban, CrowdSec и другими средствами защиты.

`bfban` не анализирует логи и не решает, является ли адрес вредоносным или
атакующим. За это отвечают Fail2ban, CrowdSec или собственный security-agent;
`bfban` применяет уже принятое решение:

```text
Fail2ban / CrowdSec / свой агент
                │
                ▼
        демон bfband + сокет Unix
                │
                ▼
        наборы и карты bpfilter
                │
                ▼
          eBPF DROP на Linux
```

В первой версии `bfban` управляет одной цепочкой bpfilter. Демон `bfband`
держит сокет Unix, сроки действия блокировок и их состояние. Если
`libbpfilter` найден через `pkg-config`, демон использует прямой C API; иначе
работает запасной режим через `bfban`/`bfcli`.

Проект распространяется под GPL-2.0-only.

Исходный движок находится в [libbpfilter](https://bpfilter.io/developers/modules/libbpfilter/libbpfilter.html),
а локальные публичные заголовки — в
[`src/libbpfilter/include/bpfilter`](https://github.com/facebook/bpfilter/tree/main/src/libbpfilter/include/bpfilter).
Режим выбирается через `BFBAN_DIRECT=auto|yes|no`, а путь к bpffs — через
`BFBAN_BPFFS`.

Практические «вау-фичи» здесь — не рекламные обещания: CIDR хранится одной
LPM-записью, Fail2ban работает через один сокет Unix демона, `bfobserve`
показывает источники нагрузки до принятия решения о блокировке, а состояние
восстанавливается после перезапуска. Автоматическое обнаружение атак и защита
у провайдера от DDoS намеренно не входят в текущую область применения.

Конечный список закрытых пунктов и release-gates находится в
[`docs/roadmap.md`](docs/roadmap.md).

## Область применения

`bfban` нужен пограничному серверу Linux, которому требуется динамический
список блокировки отдельных IP-адресов или сетей CIDR. Решение о блокировке
могут принимать Fail2ban, CrowdSec, администратор или проверенный список
угроз. Демон централизует обновления, хранит состояние и сроки действия
блокировок и применяет принятое решение через bpfilter, не заменяя основной
межсетевой экран сервера.

`bfban` не является анализатором журналов, полноценным межсетевым экраном с
учётом состояний соединений, заменой NAT/conntrack, автоматическим
классификатором ботнетов или средством восстановления уже заполненного
внешнего канала. Для этого нужны основной межсетевой экран, настройки самого
приложения, правила у провайдера или очистка трафика до сервера.

## Роль в anti-DDoS-схеме

`bfban` — это enforcement-слой многоуровневой anti-DDoS-схемы:

```text
трафик/журналы/список угроз
       │
       ▼
решение: Fail2ban, CrowdSec, администратор, список угроз
       │
       ▼
bfban: обновление наборов точных IP и сетей CIDR
       │
       ▼
bpfilter: DROP в выбранной точке подключения ядра
```

| Ситуация | Что делает `bfban` | Чего он не делает |
|---|---|---|
| Известный вредоносный IP или CIDR | применяет L3/L4 deny-запись | сам не ищет IOC |
| Брутфорс SSH/web | принимает решение Fail2ban и применяет бан | не читает логи и не выбирает пороги |
| Высокая скорость пакетов от источника, видимая на сервере | `bfobserve` показывает наиболее активные источники, оператор применяет бан | не гарантирует видимость каждого пакета и не классифицирует атаку автоматически |
| Распределённая атака или подмена адресов | отбрасывает известные источники в выбранной точке подключения | не устраняет подмену адресов и не восстанавливает забитый внешний канал |
| Канал уже заполнен | локально почти ничего | не заменяет фильтрацию или очистку трафика у провайдера |

По умолчанию используется `NF_LOCAL_IN`: это защита сервисов, доставляемых
на этот сервер, а не фильтрация всего транзитного трафика маршрутизатора. Под
«ранним ingress» здесь понимается receive path сетевого интерфейса: XDP
срабатывает до обычного Linux network stack, создания и обработки пакета как
`skb`, то есть DROP может произойти до Netfilter и conntrack. Для такого DROP
на поддерживаемом интерфейсе можно явно выбрать XDP:

```sh
export BFBAN_HOOK='BF_HOOK_XDP{ifindex=2}'
sudo bfban init
```

`ifindex` нужно взять из `bfobserve --list-interfaces`. Management-доступ
держите на другом интерфейсе и отдельно измеряйте native XDP и generic XDP.
XDP — ранняя точка обработки входящих пакетов выбранного интерфейса, а не
фильтр исходящих сокетов. Он может уменьшить нагрузку на сервер, но не
увеличивает пропускную способность уже забитого внешнего канала. См.
[размещение точек обработки в bpfilter](https://bpfilter.io/usage/explanation/hooks.html)
и [научную статью про XDP](https://doi.org/10.1145/3281411.3281443).

## CIDR — полноценная поддержка сетей

CIDR — это рабочий формат ввода, а не только пример в документации:

```sh
sudo bfban add 203.0.113.10       # один IPv4-адрес
sudo bfban add 203.0.113.0/24     # IPv4-префикс
sudo bfban add 2001:db8::1        # один IPv6-адрес
sudo bfban add 2001:db8::/32      # IPv6-префикс
sudo bfban list
sudo bfban add-many /path/to/addresses.txt  # batch-обновление
```

При `bfban init` создаются четыре независимых набора:

| Ввод | bpfilter set | Matcher |
|---|---|---|
| IPv4-адрес | `banlist4` | `ip4.saddr` |
| IPv4 CIDR | `banlist4net` | `ip4.snet` |
| IPv6-адрес | `banlist6` | `ip6.saddr` |
| IPv6 CIDR | `banlist6net` | `ip6.snet` |

Точные адреса и префиксы разделены: сеть не разворачивается в тысячи
отдельных IP, а проверяется через набор префиксов LPM bpfilter. CIDR сохраняется
в файле состояния и восстанавливается `bfband` после перезапуска.
`add-many` проверяет и удаляет дубликаты, группирует записи по типу набора и
выполняет один `chain update-set` на группу (при большом файле — чанками).
Это дешевле, чем запускать `bfban add` для каждой строки списка. Обновление
каждой группы атомарно, но весь файл не является одной глобальной транзакцией.
CIDR нормализуется перед сохранением: например, `192.0.2.17/24`
превращается в `192.0.2.0/24`, поэтому эквивалентные сети не дублируются.

## Конфигурация и установка

Для этого небольшого проекта отдельный Autotools/CMake не нужен: есть POSIX
`configure` и обычный Makefile.

```sh
./configure --prefix=/usr/local
make
sudo make install
sudo systemctl daemon-reload
sudo systemctl enable --now bfband
```

Основные параметры находятся в `/etc/bfban/bfban.env`: путь к `bfcli`,
сокету Unix, файлу состояния, цепочке и точке обработки.

## Пошаговая методика применения

### 1. Проверить хост

Проверяйте фактически запущенное ядро, `libbpf` и доступные интерфейсы:

```sh
uname -r
pkg-config --modversion libbpf
mountpoint /sys/fs/bpf
sudo bfobserve --list-interfaces
```

Текущая тестовая матрица — Linux 6.6+, `libbpf` 1.2+ и bpfilter с точками
обработки, совместимыми с этим ядром. Это исходная база для проверки, а не
универсальное утверждение о минимальной версии, которое можно вывести из одного
`bfban`. Примеры
подходящих базовых ядер: Ubuntu 24.04 (6.8),
Debian 13 (6.12), Fedora 40 (6.8), RHEL/Rocky/Alma 10 (6.12), Ubuntu 22.04 с
HWE 6.8. RHEL/Rocky/Alma 9 (5.14) и Debian 12 (6.1) требуют нового
поддерживаемого ядра или backport.

Полный англоязычный план стенда и проверки для Rocky Linux 10, Debian 13 и
Ubuntu 24.04 находится в [`docs/validation-lab.md`](docs/validation-lab.md).
Rocky Linux 9 подходит для проверки запасной сборки, но не для подтверждения
целевого kernel compatibility.

### 2. Собрать и установить

Зависимости разделяются по назначению:

| Сценарий | Что требуется |
|---|---|
| Сборка `bfban` с запасным режимом | C-компилятор, заголовочные файлы libc, `make` |
| Сборка `bfband` с прямым API | `bpfilter`, `bpfilter-devel`, `pkg-config` |
| Сборка bpfilter из исходников | CMake, GCC, Clang, `libbpf-devel`, Bison, Flex, `sed`, `xxd` |
| Работа фильтра | `bfcli`/`bpfilter`, смонтированная BPF-файловая система, root |
| Интеграция с Fail2ban | `fail2ban` и systemd, если используется готовое действие |
| Проверка и диагностика | `bpftool`, `iproute`, `ethtool`, `perf`, `sar`/`sysstat` |

На Fedora или RHEL-подобной системе с подключённым EPEL сначала попробуйте
пакеты bpfilter:

```sh
sudo dnf install -y epel-release
sudo dnf install -y bpfilter bpfilter-devel
command -v bfcli
pkg-config --modversion bpfilter
pkg-config --cflags --libs bpfilter
```

`bpfilter` устанавливает `bfcli` и библиотеку для работы, а `bpfilter-devel` —
заголовочные файлы и метаданные для сборки `bfband` с прямым API. Если пакета нет
для выбранного дистрибутива, собирайте bpfilter по
[официальной инструкции](https://bpfilter.io/developers/build.html).

Короткий вариант сборки из исходников:

```sh
cmake -S /path/to/bpfilter -B /tmp/bpfilter-build \
  -DNO_DOCS=ON -DNO_TESTS=ON -DNO_CHECKS=ON \
  -DCMAKE_INSTALL_PREFIX=/usr/local
cmake --build /tmp/bpfilter-build -j"$(nproc)"
sudo cmake --install /tmp/bpfilter-build
sudo ldconfig
```

```sh
cd ~/bfban
./configure --prefix=/usr/local
make
sudo make install
```

Сборка идёт в отдельный каталог `build/`. Выбранный путь установки также
попадает в сгенерированные файлы systemd и `/etc/bfban/bfban.env`, поэтому
нестандартный путь не оставляет `ExecStart` с ошибочной ссылкой на `/usr/local`.

По умолчанию `bfcli` ищется в prefix, выбранном при установке. Другой путь
можно указать через `BFBAN_BPFCLI` в `/etc/bfban/bfban.env`. После установки
libbpfilter повторно запустите `./configure`: он обнаружит модуль pkg-config
и включит прямой C API для демона. Это убирает fork/exec при каждой блокировке
и разблокировке, но само по себе не доказывает ускорение обработки пакетов.

Если bpfilter собран из исходников, но ещё не установлен в настроенный prefix,
задайте `PKG_CONFIG_PATH` на каталог с `bpfilter.pc` и проверьте, что его
`prefix`, `includedir` и `libdir` указывают на одно дерево установки. Файл
`.pc` из build-каталога со старым `prefix=/usr/local` может обнаружиться, но
затем привести к ошибке компиляции.

### 3. Запустить systemd-демон

```sh
sudo systemctl daemon-reload
sudo systemctl enable --now bfband.service
sudo systemctl status bfband.service
sudo journalctl -u bfband.service -b --no-pager
sudo bfbandctl ping
```

Unit создаёт `/run/bfban` для сокета и `/var/lib/bfban` для состояния. Сейчас
демон запускается от `root`, поскольку программная часть загружает и изменяет BPF
объекты. Не включайте вслепую `ProtectSystem=strict` и не удаляйте
`CAP_BPF`/`CAP_NET_ADMIN`: это может сломать загрузку или обновление объектов.
Параметры systemd описаны в [systemd.exec](https://www.freedesktop.org/software/systemd/man/latest/systemd.exec).

### 4. Создать и проверить цепочку

```sh
sudo bfbandctl init
sudo bfban add 203.0.113.10
sudo bfban list
sudo bfcli chain get --name bfban_input
sudo bfban remove 203.0.113.10
```

Для сухого теста используйте документационные сети `203.0.113.0/24` и
`2001:db8::/32`. На рабочем сервере держите консольный доступ или вторую SSH
сессию. `bfban flush` очищает динамическую chain.

### 5. Подключить Fail2ban

Создайте `/etc/fail2ban/jail.d/sshd-bfban.local`:

```ini
[sshd-bfban]
enabled = true
filter = sshd
backend = systemd
port = ssh
maxretry = 5
findtime = 10m
bantime = 1h
banaction = bfban
```

Проверьте конфигурацию:

```sh
sudo fail2ban-client reload
sudo fail2ban-client status sshd-bfban
sudo bfbandctl list
sudo journalctl -u fail2ban -u bfband -f
```

Fail2ban отвечает за фильтры журналов, пороги, список разрешённых адресов и
срок блокировки; `bfban` только применяет принятое решение. В первой версии
цепочка и файл состояния общие, поэтому несколько профилей Fail2ban могут
мешать друг другу через `actionstop`.

### 6. Определить источник нагрузки

```sh
ip -s link
sar -n DEV 1
ethtool -S eno1
ss -s
conntrack -S
nstat -az
sudo bfobserve --interface eno1 --seconds 30 --top 20
sudo bfobserve --interface eno1 --seconds 30 --suggest --min-pps 1000
```

`bfobserve` ничего не блокирует: он показывает IP-источники, скорость пакетов, байты,
SYN/RST, UDP и последний порт назначения. Команда `--suggest` только печатает
варианты `bfban add`. По умолчанию учитывается входящий трафик и исключаются
`PACKET_OUTGOING`; для аудита исходящего трафика используйте
`--direction egress`, а для обоих направлений — `--direction both`. Перед
блокировкой проверьте список разрешённых адресов, NAT/CDN, порт, протокол и
независимый список угроз.

### 7. Применить CIDR или список угроз и уметь откатить

```sh
sudo bfban add 203.0.113.0/24
./scripts/fetch-threat-feed.sh --output=/tmp/feodo.txt
less /tmp/feodo.txt
sudo ./scripts/fetch-threat-feed.sh --apply
sudo bfban remove 203.0.113.10
sudo bfbandctl flush
```

Не блокируйте географию или ASN как замену проверенным признакам компрометации.
Для объёмной DDoS-атаки, которая заполняет канал, нужна фильтрация у
провайдера или очистка трафика: локальный сервер уже не может вернуть
пропускную способность канала.

## Как понять, откуда идёт DDoS

`bfban` сам по себе **не обнаруживает DDoS**. Он получает уже принятое решение
о блокировке. Источник атаки сначала нужно определить средствами наблюдения
за трафиком.

Быстрая последовательность:

```sh
# нагрузка на интерфейсы и ошибки
ip -s link
sar -n DEV 1
ethtool -S eth0

# состояние TCP/UDP и conntrack
ss -s
conntrack -S
nstat -az
```

Для поиска наиболее активных IPv4-источников во входящем трафике можно
использовать `tshark`:

```sh
sudo tshark -ni eth0 -a duration:30 -f 'ip' \
  -T fields -e ip.src 2>/dev/null |
  sort | uniq -c | sort -nr | head -50
```

Затем нужно проверить наиболее активные источники по независимым признакам:
порту назначения, флагам TCP, доле новых соединений, скорости и наличию в
известном списке угроз. Автоматически блокировать самый частый IP опасно: это может быть NAT,
прокси, CDN или легитимный клиент.

### Ограничение наблюдения при XDP

Если пакет отбрасывается в штатном режиме XDP драйвера, он может не дойти до обычного сетевого
стека и не попасть в `tcpdump`. Поэтому для расследования нужно либо временно
наблюдать трафик до включения XDP, либо иметь отдельную карту или кольцевой
буфер телеметрии, которые передают IP-адрес источника, протокол, порт и
счётчики. В текущей версии `bfban` такой телеметрии по источникам нет:
счётчики цепочки показывают количество совпадений, но не список наиболее
активных источников.

Для промышленного варианта в дальнейшем нужен отдельный `bfobserve` на eBPF:

```text
сетевой адаптер → карта наблюдения XDP → список источников в пользовательском
пространстве → решение администратора → список блокировки bfban
```

Это разделяет обнаружение атаки и применение блокировки и снижает риск
самоблокировки.

Методика по TCP-очередям, окнам, SYN-cookie и памяти описана в
[`docs/tcp-ddos-tuning.md`](docs/tcp-ddos-tuning.md). `bfban` не заменяет
настройку очереди TCP и фильтрацию у провайдера, если перегружен сам внешний
канал.

## Практическая возможность: `bfobserve`

`bfobserve` — режим наблюдения: он не блокирует адреса, а за короткий
промежуток времени собирает список наиболее активных источников и подсказывает
следующие действия. Текущая версия использует AF_PACKET и требует `root` или
`CAP_NET_RAW`; это наблюдатель в пользовательском пространстве, а не карта
телеметрии XDP.

Сначала посмотреть интерфейсы:

```sh
sudo bfobserve --list-interfaces
```

Пример вывода:

```text
Available interfaces:
  IFACE            STATE       MTU     COMMAND
  lo               up/running  65536   sudo bfobserve -i lo
  eth0             up/running  1500    sudo bfobserve -i eth0
  wg0              up           1420   sudo bfobserve -i wg0
```

Затем запустить наблюдение на WAN-интерфейсе:

```sh
sudo bfobserve --interface eth0 --seconds 30 --top 20
```

Отчёт показывает:

```text
#    SOURCE                                  PACKETS        BYTES        PPS        SYN        UDP    DPORT
1    198.51.100.20                             82000      61.2 MB       2733      81000          0       22
2    203.0.113.44                              47000      28.4 MB       1566          0      46000      443
```

Для automation/SIEM:

```sh
sudo bfobserve --interface eth0 --seconds 30 --top 100 --json
```

Для осторожных рекомендаций:

```sh
sudo bfobserve --interface eth0 --seconds 30 \
  --suggest --min-pps 1000
```

Команда только напечатает предложения вида:

```text
bfban add 198.51.100.20  # 2733 pps, 81000 SYN, 0 UDP
```

Администратор проверяет источник, список разрешённых адресов и список угроз,
после чего сам решает, выполнять ли `bfban add`. Это сделано намеренно:
автоматическая блокировка только по частоте может заблокировать NAT, CDN или
легитимного клиента.

## Тестовая матрица ядра и дистрибутивов

Для первой версии зафиксирована такая проверочная база. Это не универсальное
утверждение о минимальной версии ядра самого `bfban`: совместимость зависит от
версии bpfilter, hook и конфигурации ядра.

| Компонент | Требование |
|---|---|
| Linux kernel | **6.6 или новее для целевой проверки** |
| libbpf | **1.2 или новее для прямого профиля** |
| BPF token mode | не требуется текущей реализацией |
| пользовательская часть | `clang`, `libbpf`, `bpftool`/BPF-файловая система по конфигурации системы |

Проверять нужно фактическое запущенное ядро, а не только версию дистрибутива:

```sh

pkg-config --modversion libbpf
mountpoint /sys/fs/bpf
```

### Почему именно eBPF/XDP

Научное и инженерное обоснование не в том, что любой eBPF-код быстрее
iptables. Выигрыш возникает в конкретной точке обработки и при конкретном
профиле нагрузки. Академическая база — статья:

> Toke Høiland-Jørgensen, Jesper Dangaard Brouer, Daniel Borkmann, John
> Fastabend, Tom Herbert, David Ahern и David Miller. «The eXpress Data Path:
> Fast Programmable Packet Processing in the Operating System Kernel». ACM
> CoNEXT 2018. DOI: [10.1145/3281411.3281443](https://doi.org/10.1145/3281411.3281443).

1. XDP вызывается на раннем пути приёма пакета и может вернуть `XDP_DROP` до
   обычной обработки сетевым стеком.
2. Linux может JIT-компилировать eBPF в машинный код, но результат зависит от
   архитектуры и конфигурации ядра.
3. Точные адреса хранятся в хеш-таблицах, а CIDR проверяется по самому
   длинному совпадающему префиксу (LPM), без разворачивания сети в отдельные IP.
4. `chain update-set` в bpfilter атомарен и сохраняет счётчики, но сам bpfilter
   при этом заново создаёт BPF-программу с новым содержимым набора. Прямой API
   убирает fork/exec и разбор командной строки, но не делает обновление ядра
   бесплатным.

Это делает решение перспективным для раннего отбрасывания L3/L4-пакетов,
больших списков блокировки и высокой скорости пакетов. Это не доказывает
преимущество над современным nftables: nftables тоже поддерживает наборы,
динамические наборы, счётчики и ограничение скорости по источнику. Поэтому
обязательна контрольная серия измерений:

```text
legacy iptables  vs  nftables  vs  bpfilter Netfilter  vs  bpfilter XDP
```

Сравнивать нужно одинаковые правила и нагрузку: размер списка блокировки,
число пакетов в секунду,
accept/drop ratio, CPU, latency, IPv4/IPv6 и наличие counters/logging.

Первичные источники описывают раннее выполнение XDP и live-frame режим в
[Linux kernel BPF documentation](https://docs.kernel.org/bpf/bpf_prog_run.html),
LPM в [Linux LPM-trie documentation](https://docs.kernel.org/bpf/map_lpm_trie.html),
а требования и поддержка конкретных hooks должны проверяться по kernel API,
который использует сам bpfilter.

## Зачем это нужно

Типичная схема Fail2ban добавляет или удаляет отдельные правила firewall при
каждом бане. При большом количестве адресов это приводит к длинным цепочкам,
частым изменениям ruleset и дополнительной работе control plane.

`bfban` держит постоянные наборы адресов:

```text
одна eBPF chain
наборы banlist4/banlist6 и banlist4net/banlist6net
много IP-адресов и CIDR-сетей внутри этих sets
```

Добавление или удаление адреса меняет содержимое set, а не структуру всей
программы. В bpfilter для этого уже есть операция `chain update-set`.

Fail2ban предоставляет action-команды `actionstart`, `actionban` и
`actionunban`; именно через такой action `bfban` интегрируется с Fail2ban.
См. пример в [etc/fail2ban/action.d/bfban.conf](etc/fail2ban/action.d/bfban.conf)
и официальные actions Fail2ban: <https://github.com/fail2ban/fail2ban/tree/master/config/action.d>.

## Как это интегрируется с Fail2ban

Fail2ban и `bfban` выполняют разные роли:

```text
лог sshd/nginx/etc.
        │
        ▼
Fail2ban filter
        │ считает maxretry за findtime
        ▼
Fail2ban jail принимает решение о бане
        │
        ├── actionstart  → создать bpfilter chain и banlist
        ├── actionban    → добавить IP в banlist
        ├── actionunban  → удалить IP из banlist
        └── actionstop   → удалить chain
```

`bfban` не читает логи и не знает, почему адрес был заблокирован. Он получает
от Fail2ban только команды. Например, при пяти неудачных SSH-входах за десять
минут Fail2ban вызывает:

```sh
bfban add 203.0.113.10
```

Когда заканчивается `bantime`, Fail2ban вызывает:

```sh
bfban remove 203.0.113.10
```

В текущей версии эти команды вызывают `bfcli chain update-set`. Поэтому eBPF
программа остаётся загруженной, а изменяется только содержимое соответствующего
именованного набора.
Fail2ban уже управляет временем жизни бана; отдельный TTL в MVP не нужен.

### Установка action

После сборки установить бинарник и action:

```sh
cd ~/bfban
make
sudo make install
```

Проверить, что доступны:

```text
/usr/local/sbin/bfban   # или PREFIX/sbin/bfban
/etc/fail2ban/action.d/bfban.conf
```

### Пример jail для SSH

Создать `/etc/fail2ban/jail.d/sshd-bfban.local`:

```ini
[sshd-bfban]
enabled = true
filter = sshd
backend = systemd
port = ssh
maxretry = 5
findtime = 10m
bantime = 1h
banaction = bfban
```

Затем перезапустить Fail2ban:

```sh
sudo systemctl restart fail2ban
sudo fail2ban-client status sshd-bfban
```

При старте jail action выполнит `bfban init`. При бане и разбане IP будут
вызваны `actionban` и `actionunban` из
`/etc/fail2ban/action.d/bfban.conf`.

### Важное ограничение текущего MVP

Сейчас используется одна глобальная цепочка `bfban_input` и один файл состояния.
Поэтому безопасный вариант — один jail, например SSH. Если подключить
несколько jail одновременно, они будут использовать общий список, а
`actionstop` одного jail может очистить баны другого.

Текущий `bfband` всё ещё использует одну глобальную chain; namespace по имени
jail будет добавлен позже. Поэтому до появления namespaces следует либо
использовать один общий jail/action, либо не включать `actionstop` на
отдельных jail.

### Проверка работы

Состояние Fail2ban:

```sh
sudo fail2ban-client status sshd-bfban
```

Список адресов, переданных в bpfilter:

```sh
sudo bfban list
```

Состояние bpfilter-chain:

```sh
sudo bfcli chain get --name bfban_input
```

В counters chain можно увидеть, сколько пакетов было отброшено. Для
диагностики сначала рекомендуется использовать `bantime = 10m` и проверять
chain вручную, а уже затем включать длительные баны.

## Какие преимущества

### Быстрый поиск

Адрес проверяется внутри скомпилированной eBPF-программы и соответствующего
именованного набора. Это особенно полезно для больших списков блокировки и
частых обновлений.

### Раннее отбрасывание

В режиме XDP пакет можно отбросить на самом раннем этапе приёма сетевой
картой — до обычной обработки сетевым стеком. Такой режим полезен для
высокой скорости пакетов и простых списков L3/L4. Для XDP нужны совместимые драйвер и
режим подключения; XDP не заменяет NAT и conntrack.

### Атомарное обновление

Обновление chain не должно оставлять окно без фильтрации. Для массовых
изменений используется обновление set, а для изменения программы — атомарный
`chain update`.

### Меньше конфликтов с основным firewall

`bfban` может работать отдельным слоем рядом с iptables/nftables. Основной
межсетевой экран продолжает отвечать за NAT, conntrack и постоянную политику,
а `bfban` — за динамический список блокировки.

### Фильтрация по cgroup

Сам bpfilter также умеет cgroup hooks. Это позволяет в будущем применять
политику не только к интерфейсу, но и к группе процессов.

## Что это не делает

`bfban` не является полной защитой от объёмной DDoS-атаки. Если канал уже
забит, локальный сервер Linux не сможет устранить проблему — нужна фильтрация
или очистка трафика у провайдера.

`bfban` также не заменяет полноценный межсетевой экран с отслеживанием
состояния соединений. NAT, conntrack,
маршрутизация и постоянные правила должны оставаться в nftables/iptables или
другом основном firewall.

Для ограничения скорости по источнику потребуется отдельная реализация
алгоритма token bucket и состояния в картах BPF. В текущей версии этого нет.

## Память

Память состоит из трёх частей:

1. `bfband` держит таблицу адресов и сроки блокировки в пользовательской
   памяти. При текущем лимите `65536` записей это примерно **4.5 MiB**
   зарезервированной памяти, плюс обычная память процесса.
2. `bfcli`/`libbpfilter` временно используют память при загрузке или обновлении
   цепочки.
3. Сама карта BPF живёт в памяти ядра. Для точной оценки нужно смотреть
   `bpftool map show` и `bpftool map dump`; расход зависит от типа карты, размера
   ключа, числа элементов и накладных расходов распределителя памяти ядра.

Грубая инженерная оценка для списка блокировки — десятки байт памяти ядра на IPv4
адрес и больше для IPv6/LPM. Демон использует bounded open-addressing index для
быстрого поиска ADD/DEL/TTL; таблица адресов остаётся ограниченной. То есть
`100000` адресов обычно означают единицы мегабайт, а не сотни мегабайт, но
это нужно подтвердить измерением на целевом ядре. Таблица уже размещается в
динамической памяти и ограничена лимитом `65536` записей; для промышленной
эксплуатации нужны измерения на целевом ядре и наблюдение за фактическим
размером карты BPF.

## CIDR и сети

Без CIDR полноценный загрузчик списков угроз неполон. Важно, что bpfilter уже
поддерживает `ip4.snet`, `ip6.snet` и наборы LPM. Поэтому для списка блокировки
нужно разделять четыре набора:

```text
banlist4      — точные IPv4
banlist4net   — IPv4 CIDR
banlist6      — точные IPv6
banlist6net   — IPv6 CIDR
```

`bfban` теперь принимает как `203.0.113.10`, так и `203.0.113.0/24`, а при
инициализации цепочки создаёт соответствующие наборы точных адресов и LPM.
Spamhaus DROP можно будет подключить после добавления загрузчика с поддержкой
CIDR; текущий пример
Feodo Tracker содержит IPv4-адреса и работает уже сейчас.

## Проверка на списках угроз

Не следует блокировать «китайские сети» только по географии или ASN: это не
признак ботнета и даст много ложных срабатываний. Для воспроизводимой проверки
нужны списки признаков, характерных для конкретных ботнетов. Скрипт
[`scripts/fetch-threat-feed.sh`](scripts/fetch-threat-feed.sh) по умолчанию
использует рекомендованный список управляющих узлов Feodo Tracker, скачивает и
проверяет IPv4-адреса,
но ничего не блокирует без явного `--apply`.

```sh
./scripts/fetch-threat-feed.sh --output=/tmp/feodo.txt
less /tmp/feodo.txt
sudo ./scripts/fetch-threat-feed.sh --apply
```

Feodo Tracker описывает адреса как подтверждённые управляющие узлы ботнета и
предупреждает, что расширенный исторический список имеет более высокий риск
ложных срабатываний:
<https://feodotracker.abuse.ch/blocklist/>.
Spamhaus DROP можно использовать для отдельного CIDR-aware importer, но его
обновление должно быть автоматическим и не чаще разрешённой частоты:
<https://www.spamhaus.org/faqs/do-not-route-or-peer-drop/>.

Эти списки предназначены для защитной проверки и подключения к списку
блокировки, а не для активного сканирования или атак на перечисленные адреса.

## Демон `bfband`

Демон `bfband`:

- слушать Unix socket `/run/bfban/bfban.sock`;
- принимать `ADD`, `DEL`, `LIST`, `FLUSH`;
- поддерживать TTL для банов;
- восстанавливать состояние после перезапуска;
- сериализовать изменения set;
- передавать команды через один Unix-сокет;
- ограничивать доступ Unix-пермишенами и root/group policy.

Текущий текстовый API:

```text
ADD 203.0.113.10 3600
DEL 203.0.113.10
ADD_MANY 203.0.113.10 198.51.100.0/24
LIST
FLUSH
```

Fail2ban вызывает только тонкий action-клиент `bfbandctl`, а не управляет
eBPF objects самостоятельно.

Запуск после установки:

```sh
sudo systemctl enable --now bfband
sudo bfbandctl ping
```

Если доступен `libbpfilter`, `ADD_MANY` группирует exact- и CIDR-записи по
семейству адресов и обновляет set через прямой C API. Без библиотеки сохраняется
совместимый fallback через `bfban`/`bfcli`.

Перед сообщением об успешной записи демон выполняет `fsync` файла и пытается
выполнить `fsync` каталога.
Изменение ядра и переименование файла состояния не образуют одну физическую
транзакцию, поэтому при ошибке сохранения выполняется попытка отката в ядре,
а при запуске демона записанное состояние можно применить повторно. Если
компенсирующий откат не удался, демон сообщает об этом и не принимает новые
изменения до успешного явного `INIT`.

Команда Fail2ban `actioncheck` проверяет доступность Unix-сокета daemon. Это не
проверка каждого packet hook и не benchmark datapath; восстановление выполняют
`bfbandctl init` и reconcile daemon.

## Вау-фича: понятная диагностика источника атаки

`bfobserve` — наблюдатель трафика для ответа на практический вопрос «откуда
идёт нагрузка?». Он за короткое окно показывает top-N источников, PPS, байты,
SYN, UDP и последний destination port, а `--suggest` печатает готовые команды
для передачи подозрительных адресов в `bfban`.

Сначала администратор выбирает интерфейс понятным списком:

```sh
sudo bfobserve --list-interfaces
sudo bfobserve --interface eth0 --seconds 30 --top 20
sudo bfobserve --interface eth0 --seconds 30 --top 20 --suggest --min-pps 100
sudo bfobserve --interface eth0 --seconds 30 --json
```

Пример вывода интерфейсов:

```text
Available interfaces:
  IFACE            STATE       MTU     COMMAND
  lo               up/running  65536   sudo bfobserve -i lo
  eth0             up/running  1500    sudo bfobserve -i eth0
```

Это именно диагностический слой: он не блокирует адрес автоматически и не
выдаёт «ботнет» по одному признаку. Администратор видит источник, проверяет
порт/протокол и затем применяет адрес через `bfban`, Fail2ban или отдельную
политику. Нужны `root` или `CAP_NET_RAW`; текущая версия использует безопасный
захват AF_PACKET, поэтому это не обещание, что вся объёмная атака будет видна
после аппаратной обработки или фильтрации у провайдера.

## Когда это имеет смысл

Проект имеет смысл как:

- средство применения решений Fail2ban/CrowdSec;
- быстрый динамический список блокировки на пограничном сервере Linux;
- уровень блокировки XDP/TC для высокой скорости пакетов;
- специализированная фильтрация, которую неудобно выражать обычными
  firewall-правилами.

Для небольшого сервера с несколькими десятками правил обычный nftables
обычно проще. Современный nftables также поддерживает наборы, сроки действия и
ограничение скорости по источнику, поэтому преимущество `bfban` нужно подтверждать
измерениями, а не предполагать заранее.
