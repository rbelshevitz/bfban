# bfban: динамические блок-листы для Linux

[English](README.md) | [Русский](README.ru.md)

## Что такое `bfban`

🛡️ `bfban` — сервис для динамического списка блокировок IP-адресов и сетей CIDR.
Fail2ban, CrowdSec, администратор или другой агент передаёт ему решение;
`bfban` хранит список, TTL и состояние, а затем применяет DROP через
bpfilter/eBPF.

🎯 Коротко: обнаружение решает, `bfban` применяет. Он не читает логи и не заменяет
основную политику межсетевого экрана.

🔗 Решение о блокировке принимают Fail2ban, CrowdSec или другой агент; `bfban`
применяет уже принятое решение:

```text
Fail2ban / CrowdSec / свой агент
                │
                ▼
        демон bfband + сокет Unix
                │
                ▼
        наборы и карты bpfilter
                │
                ▼
          eBPF DROP на Linux
```

⚙️ В первой версии `bfban` управляет одной цепочкой bpfilter. Демон `bfband`
держит сокет Unix, сроки действия блокировок и их состояние. Если
`libbpfilter` найден через `pkg-config`, демон использует прямой C API; иначе
работает запасной режим через `bfban`/`bfcli`.

Названия компонентов означают следующее: `bfban` — прямой CLI-backend для
ручных и пакетных обновлений, `bfband` — постоянно работающий демон, а
`bfbandctl` — клиент его Unix-сокета. Поставляемый action Fail2ban запускает
именно `bfbandctl`.

Проект распространяется под GPL-2.0-only.

Исходный движок находится в [libbpfilter](https://bpfilter.io/developers/modules/libbpfilter/libbpfilter.html),
а локальные публичные заголовки — в
[`src/libbpfilter/include/bpfilter`](https://github.com/facebook/bpfilter/tree/main/src/libbpfilter/include/bpfilter).
Режим выбирается через `BFBAN_DIRECT=auto|yes|no`, а путь к bpffs — через
`BFBAN_BPFFS`.

Контрольный список релиза находится в
[`docs/roadmap.md`](docs/roadmap.md).

## Практическое использование

🚀 Для работы `bfban` нужны bpfilter и запущенный сервис `bfband`. Fail2ban
необязателен: устанавливайте его только если он будет источником решений о
блокировке.

Запустите службу и проверьте временную блокировку:

```sh
sudo systemctl enable --now bfband.service
sudo /usr/sbin/bfbandctl init
sudo /usr/sbin/bfbandctl add 203.0.113.10 60
sudo /usr/sbin/bfbandctl list
sudo bfcli ruleset get
```

Есть три основных способа передавать решения:

1. **Вручную или из собственного агента.** Используйте
   `bfbandctl add IP [TTL]` и `bfbandctl remove IP`. Команда `bfban add`
   добавляет постоянную запись через CLI, если TTL демона не нужен.
2. **Fail2ban.** Установите Fail2ban, включите поставляемый action `bfban` и
   задайте в jail `banaction = bfban`. Здесь `bfban` — имя файла action, а не
   команда, которую Fail2ban запускает напрямую. Action вызывает
   `bfbandctl add/remove`, а `bfband` применяет полученные команды.
3. **Список угроз.** Запустите `scripts/fetch-threat-feed.sh` без `--apply`,
   проверьте полученный файл и список разрешённых адресов, затем примените его
   с `--apply`.

Состояние можно проверить через `bfbandctl list` и `bfcli ruleset get`.
Одну запись удаляют командой `bfbandctl remove IP`, а динамическую цепочку
очищают через `bfbandctl flush`.

## Роли Fail2ban, nftables, bpfilter и bfban

🧩 У этих компонентов разные роли:

| Компонент | Роль |
|---|---|
| Fail2ban/CrowdSec | обнаруживают подозрительную активность и принимают решение о блокировке |
| `nftables`/`iptables` | универсальные движки межсетевого экрана; они также умеют хранить динамические наборы |
| `bpfilter` | движок фильтрации, который загружает цепочки, правила и наборы как eBPF-программы |
| `bfband`/`bfban` | демон и клиент для динамических банов, TTL, состояния и наборов bpfilter |
| `NF_LOCAL_IN`/XDP | точки подключения цепочки в ядре |

Возможны две разные схемы:

```text
Fail2ban → набор nftables → точка подключения nftables
Fail2ban → bfband → набор/цепочка bpfilter → NF_LOCAL_IN или XDP
```

🔀 `bfban` — не второй межсетевой экран, который обязательно нужно ставить поверх
`nftables`. Это отдельная служба для управления динамическим списком блокировок.
При этом `nftables` может продолжать обслуживать обычную политику хоста, а
`bfban` — отдельный список источников, который часто меняется.

### Где используется eBPF

🧠 `bfband` управляет фильтром, но не обрабатывает сами пакеты. Когда добавляется
бан, демон обновляет набор bpfilter. Затем bpfilter создаёт и загружает в ядро
небольшую программу eBPF и связанные с ней внутренние таблицы (карты). После
этого каждый пакет проверяется непосредственно в ядре в выбранной точке
подключения; пакет не проходит через
`bfband`, и для него не запускается отдельный процесс в пользовательском
пространстве. `bfbandctl list` показывает состояние управления, а
`bfcli ruleset get` — загруженную цепочку фильтрации и её наборы.

✅ Практическая польза `bfban` — в контуре управления: единый API-демон, TTL,
сохранение состояния, сверка после рестарта, точные IP/CIDR-наборы и выбор
XDP для более ранней фильтрации. Если прямое подключение Fail2ban к набору
`nftables` уже закрывает все эти потребности, добавлять `bfban` не нужно.

### Что именно доказывает проверка концепции (PoC)

🔬 Проект не утверждает, что `bfban` уже является полной заменой `nftables`.
Проверка концепции подтверждает более узкое утверждение: bpfilter может применять
динамический список IP/портовых блокировок (L3/L4) на реальном хосте, а `bfban`
управляет обновлениями, TTL, восстановлением состояния и CIDR-наборами. Для
полноценной замены межсетевого экрана понадобились бы сопоставимые правила с
отслеживанием состояния, NAT, маршрутизация, журналирование, наборы условий, а также
измеренное соответствие по функциям и производительности. В v1 этого нет.

### Зачем нужна эта служба

📌 Здесь есть два разных вида преимуществ: способ фильтрации пакетов и управление
динамическим списком.

#### Преимущества обработки пакетов

| Преимущество | Практический эффект | Ограничение |
|---|---|---|
| Одна стабильная цепочка и изменяемые наборы | Добавление и удаление адреса меняет данные набора, а не создаёт отдельное правило | Наборы `nftables` дают похожую модель |
| Сопоставление CIDR по префиксу | Сеть вроде `203.0.113.0/24` проверяется как один префикс, а не разворачивается в 256 адресов | Это слой IP/портовых блокировок, а не универсальная политика межсетевого экрана |
| Ранний входящий путь | На поддерживаемом интерфейсе XDP может отбросить входящий пакет до обычного сетевого стека и Netfilter | XDP работает только на входе, зависит от драйвера и не всегда быстрее |
| Выполнение через eBPF | bpfilter превращает цепочку в BPF-программу и карты ядра, которые работают на пути пакета | Преимущество по производительности над `nftables` этим проектом не доказано |

#### Преимущества управления

| Проблема | Что даёт `bfban` |
|---|---|
| Несколько источников отправляют баны | Один API через Unix-сокет для Fail2ban, CrowdSec, списков угроз и администратора |
| Баны короткие и часто меняются | Централизованные TTL, сохранение состояния и восстановление после рестарта |
| В списке есть адреса и сети | Отдельные точные и CIDR/LPM-наборы без разворачивания сетей |
| Нельзя наращивать цепочку правил для каждого адреса | Одна стабильная цепочка bpfilter с изменяемым содержимым наборов |
| Важна точка применения | Один список можно подключить в `NF_LOCAL_IN` или явно выбрать XDP |
| Ошибка обновления не должна терять состояние | Ограниченные запросы, надёжная запись состояния, откат и сверка с ядром |

`nftables` уже умеет некоторые из этих вещей, включая наборы и TTL элементов.
`bfban` имеет смысл, когда нужны управляемый демоном жизненный цикл, единый API
для нескольких источников, интеграция с bpfilter или выбор XDP. Он не нужен
только потому, что хосту вообще требуется межсетевой экран.

Выбирайте инструмент по задаче:

| Задача | Использовать |
|---|---|
| Постоянные правила, состояния соединений, NAT и порты | `nftables` (или уже используемые правила `iptables`) |
| Совместимость с существующей конфигурацией iptables | `iptables` |
| Частые точечные и CIDR-блокировки от Fail2ban/CrowdSec/списка угроз | `bfban` |
| Один стабильный фильтр и изменяемый список блокировок | `bfban` с bpfilter/eBPF |
| Фильтрация до обычного сетевого стека на поддерживаемом интерфейсе | `bfban` с явно настроенным XDP |

## Что такое XDP

XDP (eXpress Data Path) — ранняя точка обработки входящих пакетов в Linux.
Она работает до обычного сетевого стека, Netfilter и conntrack и может сразу
вернуть `DROP`. Это может снизить нагрузку на CPU для известных источников.

XDP работает только на входе интерфейса, не фильтрует исходящие сокеты и не
поможет, если внешний канал уже заполнен. Результат зависит от драйвера и от
режима — native или generic XDP. В `bfban` XDP включается явно:

```sh
sudo env BFBAN_HOOK='BF_HOOK_XDP{ifindex=2}' /usr/sbin/bfban init
```

Индекс возьмите из `bfobserve --list-interfaces`; при проверке сохраните
отдельный административный доступ.

### Проверка совместимости с XDP

🔌 `bfban` поддерживает оба режима XDP. Для native XDP нужна поддержка драйвера
ядра. Generic XDP работает на гораздо большем числе интерфейсов, но срабатывает
позже. Конкретный режим зависит от ядра, драйвера и способа подключения; по
одному названию сетевой карты его определить нельзя.

| Режим | Где выполняется | Практический эффект |
|---|---|---|
| Native XDP (`xdpdrv`) | В драйвере сетевой карты, до превращения пакета в `skb` | Самый ранний DROP и обычно меньшая нагрузка на хост; нужна поддержка драйвера |
| Generic XDP (`xdpgeneric`) | В обычном входящем пути Linux, после превращения пакета в `skb` | Шире совместимость и удобно для проверки; теряется часть преимущества раннего DROP, обычно ниже PPS |
| Аппаратный offload | В поддерживаемом оборудовании сетевой карты | `bfban` его не выбирает; нужны конкретные карта, драйвер и поддержка offload |

Правило фильтрации одно и то же, но место выполнения разное. Native XDP может
не выполнять часть работы, которая уже произошла в generic XDP, например создание
и передачу `skb` дальше по сетевому стеку. Generic XDP остаётся настоящим XDP и
подходит для проверки или случаев без native-поддержки, но его производительность
нельзя считать эквивалентной native.

Есть и другие ограничения: native-поддержка зависит от версии драйвера в ядре,
MTU и поддержки XDP-фрагментов, уже подключённых XDP-программ и особенностей
драйвера. Аппаратный offload — отдельная возможность, это не обычный путь
`bfban`.

Сначала проверьте сам интерфейс и его драйвер:

```sh
IFACE=eno1
IFINDEX=$(cat "/sys/class/net/$IFACE/ifindex")
ip -details link show dev "$IFACE"
ethtool -i "$IFACE"
sudo bpftool feature probe dev "$IFACE"
printf 'ifindex=%s\n' "$IFINDEX"
```

В репозитории есть и готовая безопасная проверка без подключения программы:

```sh
sudo ./scripts/check-xdp.sh eno1
```

Скрипт выводит `ifindex`, сведения об интерфейсе и драйвере, проверки eBPF для
ядра и устройства, а также текущие BPF-подключения. Он не подключает программу
и не меняет правила фильтрации.

`bpftool feature probe dev` показывает доступные для устройства возможности
eBPF. Это предварительная проверка, а не доказательство, что именно эта цепочка
bpfilter подключится. Решающий тест — попробовать подключить настоящую цепочку
на тестовом интерфейсе.

Укажите выбранный интерфейс в `/etc/bfban/bfban.env`:

```ini
BFBAN_HOOK=BF_HOOK_XDP{ifindex=2}
```

Перезапустите демон и инициализируйте цепочку:

```sh
sudo systemctl restart bfband
sudo /usr/sbin/bfbandctl init
sudo bpftool net show dev "$IFACE"
sudo ip -details link show dev "$IFACE"
```

В выводе должна появиться программа XDP, подключённая к интерфейсу. Если
подключение не удалось, посмотрите `journalctl -u bfband` и верните
`NF_LOCAL_IN`. Не проводите первый тест на единственном интерфейсе управления:
ошибка XDP или неправильный список блокировок может отрезать административный
доступ. `bpftool net` или `ip -details link` иногда показывают режим подключения:
native (`xdpdrv`) или generic (`xdpgeneric`). Запишите фактический режим и
измеряйте их отдельно. `bfban` задаёт XDP hook и интерфейс, но не предоставляет
`bfban` поддерживает оба режима, но не предоставляет отдельного переключателя
между native и generic. Фактический режим выбирают ядро и драйвер — проверьте,
какой режим подключён.

Для функциональной проверки добавьте адрес второй машины, а не адрес самого
сервера, и проверьте одновременно поведение пакетов и счётчики цепочки. Сам
факт успешного подключения XDP ещё не доказывает, что нужный трафик
отбрасывается.

#### Распространённые драйверы с поддержкой native XDP

Поддержка native XDP зависит от драйвера Linux, а не только от модели сетевой
карты. На современных ядрах native XDP поддерживают, например, такие драйверы:

| Производитель или платформа | Драйверы |
|---|---|
| Intel | `igb`, `igc`, `i40e`, `ixgbe`, `ixgbevf`, `ice` |
| Mellanox/NVIDIA | `mlx4`, `mlx5` |
| Broadcom | `bnxt_en` |
| Amazon EC2 | `ena` |
| Google Cloud | `gve` |
| QLogic | `qede` |
| Netronome | `nfp` |
| VMware и виртуальные машины | `vmxnet3`, `virtio_net`, `veth`, `tun` |

Это ориентир, а не гарантия совместимости: результат зависит от версии ядра,
дистрибутивных backport, настроек драйвера, MTU и уже подключённых BPF-программ.
Сравните строку `driver:` из `ethtool -i IFACE` с таблицей, а затем выполните
реальную попытку подключения. Актуальная таблица находится в
[документации eBPF по XDP](https://docs.ebpf.io/linux/program-type/BPF_PROG_TYPE_XDP/).

## Область применения

`bfban` нужен пограничному серверу Linux, которому требуется динамический
список блокировки отдельных IP-адресов или сетей CIDR. Решение о блокировке
могут принимать Fail2ban, CrowdSec, администратор или проверенный список
угроз. Демон централизует обновления, хранит состояние и сроки действия
блокировок и применяет принятое решение через bpfilter, не заменяя основной
межсетевой экран сервера.

Fail2ban не обязателен для самого `bfban`. Он нужен только при использовании
готового Fail2ban action. Источником решений также могут быть администратор,
список угроз, CrowdSec или собственный агент безопасности.

`bfban` не является анализатором журналов, полноценным межсетевым экраном с
учётом состояний соединений, заменой NAT/conntrack, автоматическим
классификатором ботнетов или средством восстановления уже заполненного
внешнего канала. Для этого нужны основной межсетевой экран, настройки самого
приложения, правила у провайдера или очистка трафика до сервера.

## Роль в защите от DDoS

`bfban` — слой применения решений в многоуровневой защите от DDoS:

```text
трафик/журналы/список угроз
       │
       ▼
решение: Fail2ban, CrowdSec, администратор, список угроз
       │
       ▼
bfban: обновление наборов точных IP и сетей CIDR
       │
       ▼
bpfilter: DROP в выбранной точке подключения ядра
```

IOC (indicator of compromise, индикатор компрометации) — это признак уже
выявленной подозрительной активности, например IP-адрес или сеть CIDR. `bfban`
может применить такой список, но сам не формирует и не проверяет его.

| Ситуация | Что делает `bfban` | Чего он не делает |
|---|---|---|
| Известный вредоносный IP или CIDR | применяет правило L3/L4 | сам не обнаруживает вредоносный адрес |
| Брутфорс SSH/web | принимает решение Fail2ban и применяет бан | не читает логи и не выбирает пороги |
| Высокая скорость пакетов от источника, видимая на сервере | `bfobserve` показывает наиболее активные источники, оператор применяет бан | не гарантирует видимость каждого пакета и не классифицирует атаку автоматически |
| Распределённая атака или подмена адресов | отбрасывает известные источники в выбранной точке подключения | не устраняет подмену адресов и не восстанавливает забитый внешний канал |
| Канал уже заполнен | локально почти ничего | не заменяет фильтрацию или очистку трафика у провайдера |

По умолчанию используется `NF_LOCAL_IN`: это защита сервисов, доставляемых
на этот сервер, а не фильтрация всего транзитного трафика маршрутизатора. Для
более раннего DROP на поддерживаемом интерфейсе можно явно выбрать XDP:

```sh
sudo env BFBAN_HOOK='BF_HOOK_XDP{ifindex=2}' /usr/sbin/bfban init
```

`ifindex` нужно взять из `bfobserve --list-interfaces`. Административный доступ
держите на другом интерфейсе и отдельно измеряйте native XDP и generic XDP.
Подробнее см.
[размещение точек обработки в bpfilter](https://bpfilter.io/usage/explanation/hooks.html)
и [научную статью про XDP](https://doi.org/10.1145/3281411.3281443).

## CIDR — полноценная поддержка сетей

CIDR — это рабочий формат ввода, а не только пример в документации:

```sh
sudo bfban add 203.0.113.10       # один IPv4-адрес
sudo bfban add 203.0.113.0/24     # IPv4-префикс
sudo bfban add 2001:db8::1        # один IPv6-адрес
sudo bfban add 2001:db8::/32      # IPv6-префикс
sudo bfban list
sudo bfban add-many /path/to/addresses.txt  # batch-обновление
```

При `bfban init` создаются четыре независимых набора:

| Ввод | bpfilter set | Matcher |
|---|---|---|
| IPv4-адрес | `banlist4` | `ip4.saddr` |
| IPv4 CIDR | `banlist4net` | `ip4.snet` |
| IPv6-адрес | `banlist6` | `ip6.saddr` |
| IPv6 CIDR | `banlist6net` | `ip6.snet` |

Точные адреса и префиксы разделены: сеть не разворачивается в тысячи
отдельных IP, а проверяется через набор префиксов LPM bpfilter. CIDR сохраняется
в файле состояния и восстанавливается `bfband` после перезапуска.
`add-many` проверяет и удаляет дубликаты, группирует записи по типу набора и
выполняет один `chain update-set` на группу (при большом файле — чанками).
Это дешевле, чем запускать `bfban add` для каждой строки списка. Обновление
каждой группы атомарно, но весь файл не является одной глобальной транзакцией.
CIDR нормализуется перед сохранением: например, `192.0.2.17/24`
превращается в `192.0.2.0/24`, поэтому эквивалентные сети не дублируются.

## Конфигурация и установка

Для этого небольшого проекта отдельный Autotools/CMake не нужен: есть POSIX
`configure` и обычный Makefile.

```sh
./configure --prefix=/usr
make
sudo make install
sudo systemctl daemon-reload
sudo systemctl enable --now bfband
```

Основные параметры находятся в `/etc/bfban/bfban.env`: путь к `bfcli`,
сокету Unix, файлу состояния, цепочке и точке обработки.

## Пошаговая методика применения

### 1. Проверить хост

Проверяйте фактически запущенное ядро, `libbpf` и доступные интерфейсы:

```sh
uname -r
pkg-config --modversion libbpf
mountpoint /sys/fs/bpf
sudo bfobserve --list-interfaces
```

Текущая тестовая матрица — Linux 6.6+, `libbpf` 1.2+ и bpfilter с точками
обработки, совместимыми с этим ядром. Это исходная база для проверки, а не
универсальное утверждение о минимальной версии, которое можно вывести из одного
`bfban`. Примеры
подходящих базовых ядер: Ubuntu 24.04 (6.8),
Debian 13 (6.12), Fedora 40 (6.8), RHEL/Rocky/Alma 10 (6.12), Ubuntu 22.04 с
HWE 6.8. RHEL/Rocky/Alma 9 (5.14) и Debian 12 (6.1) требуют нового
поддерживаемого ядра или backport.

Полный англоязычный план стенда и проверки для Rocky Linux 10, Debian 13 и
Ubuntu 24.04 находится в [`docs/validation-lab.md`](docs/validation-lab.md).
Rocky Linux 9 подходит для проверки запасной сборки, но не для подтверждения
совместимости с целевым ядром.

### 2. Собрать и установить

Зависимости разделяются по назначению:

| Сценарий | Что требуется |
|---|---|
| Сборка `bfban` с запасным режимом | C-компилятор, заголовочные файлы libc, `make` |
| Сборка `bfband` с прямым API | `bpfilter`, `bpfilter-devel`, `pkg-config` |
| Сборка bpfilter из исходников | CMake, GCC, Clang, `libbpf-devel`, Bison, Flex, `sed`, `xxd` |
| Работа фильтра | `bfcli`/`bpfilter`, смонтированная BPF-файловая система, права root |
| Интеграция с Fail2ban | `fail2ban` и systemd, если используется готовое действие |
| Проверка и диагностика | `bpftool`, `iproute`, `ethtool`, `perf`, `sar`/`sysstat` |

На Fedora или RHEL-подобной системе с подключённым EPEL сначала попробуйте
пакеты bpfilter:

```sh
sudo dnf install -y epel-release
sudo dnf install -y bpfilter bpfilter-devel
command -v bfcli
pkg-config --modversion bpfilter
pkg-config --cflags --libs bpfilter
```

`bpfilter` устанавливает `bfcli` и библиотеку для работы, а `bpfilter-devel` —
заголовочные файлы и метаданные для сборки `bfband` с прямым API. Если пакета нет
для выбранного дистрибутива, собирайте bpfilter по
[официальной инструкции](https://bpfilter.io/developers/build.html).

Короткий вариант сборки из исходников:

```sh
cmake -S /path/to/bpfilter -B /tmp/bpfilter-build \
  -DNO_DOCS=ON -DNO_TESTS=ON -DNO_CHECKS=ON \
  -DCMAKE_INSTALL_PREFIX=/usr/local
cmake --build /tmp/bpfilter-build -j"$(nproc)"
sudo cmake --install /tmp/bpfilter-build
sudo ldconfig
```

```sh
cd ~/bfban
./configure --prefix=/usr
make
sudo make install
```

Сборка идёт в отдельный каталог `build/`. Выбранный путь установки также
попадает в сгенерированные файлы systemd и `/etc/bfban/bfban.env`, поэтому
при нестандартном prefix `ExecStart` и пути к утилитам остаются согласованными.

По умолчанию `bfcli` ищется в prefix, выбранном при установке. Другой путь
можно указать через `BFBAN_BPFCLI` в `/etc/bfban/bfban.env`. После установки
libbpfilter повторно запустите `./configure`: он обнаружит модуль pkg-config
и включит прямой C API для демона. Это убирает fork/exec при каждой блокировке
и разблокировке, но само по себе не доказывает ускорение обработки пакетов.

Если bpfilter собран из исходников, но ещё не установлен в настроенный prefix,
задайте `PKG_CONFIG_PATH` на каталог с `bpfilter.pc` и проверьте, что его
`prefix`, `includedir` и `libdir` указывают на одно дерево установки. Файл
`.pc` из build-каталога со старым `prefix=/usr/local` может обнаружиться, но
затем привести к ошибке компиляции.

### 3. Запустить systemd-демон

```sh
sudo systemctl daemon-reload
sudo systemctl enable --now bfband.service
sudo systemctl status bfband.service
sudo journalctl -u bfband.service -b --no-pager
sudo bfbandctl ping
```

Unit создаёт `/run/bfban` для сокета и `/var/lib/bfban` для состояния. Сейчас
демон запускается от `root`, поскольку программная часть загружает и изменяет BPF
объекты. Не включайте вслепую `ProtectSystem=strict` и не удаляйте
`CAP_BPF`/`CAP_NET_ADMIN`: это может сломать загрузку или обновление объектов.
Параметры systemd описаны в [systemd.exec](https://www.freedesktop.org/software/systemd/man/latest/systemd.exec).

### 4. Создать и проверить цепочку

```sh
sudo bfbandctl init
sudo bfban add 203.0.113.10
sudo bfban list
sudo bfcli chain get --name bfban_input
sudo bfban remove 203.0.113.10
```

Для сухого теста используйте документационные сети `203.0.113.0/24` и
`2001:db8::/32`. На рабочем сервере держите консольный доступ или вторую SSH
сессию. `bfban flush` очищает содержимое динамической цепочки.

### 5. Подключить Fail2ban

Путь передачи блокировки выглядит так:

```text
лог sshd/nginx → фильтр и jail Fail2ban
    → actionban: bfbandctl add <ip>
    → Unix-сокет bfband → набор bpfilter/eBPF → DROP
```

Когда заканчивается `bantime`, Fail2ban вызывает `actionunban`:
`bfbandctl remove <ip>`. Поэтому action не передаёт TTL: срок блокировки
контролирует сам Fail2ban.

Создайте `/etc/fail2ban/jail.d/sshd-bfban.local`:

```ini
[sshd-bfban]
enabled = true
filter = sshd
backend = systemd
port = ssh
maxretry = 5
findtime = 10m
bantime = 1h
banaction = bfban
```

Проверьте конфигурацию:

```sh
sudo fail2ban-client reload
sudo fail2ban-client status sshd-bfban
sudo bfbandctl list
sudo journalctl -u fail2ban -u bfband -f
```

Fail2ban отвечает за фильтры журналов, пороги, список разрешённых адресов и
срок блокировки; `bfban` только применяет принятое решение. В первой версии
цепочка и файл состояния общие, поэтому несколько профилей Fail2ban могут
мешать друг другу через `actionstop`.

### 6. Определить источник нагрузки

```sh
ip -s link
sar -n DEV 1
ethtool -S eno1
ss -s
conntrack -S
nstat -az
sudo bfobserve --interface eno1 --seconds 30 --top 20
sudo bfobserve --interface eno1 --seconds 30 --suggest --min-pps 1000
```

`bfobserve` ничего не блокирует: он показывает IP-источники, скорость пакетов, байты,
SYN/RST, UDP и последний порт назначения. Команда `--suggest` только печатает
варианты `bfban add`. По умолчанию учитывается входящий трафик и исключаются
`PACKET_OUTGOING`; для аудита исходящего трафика используйте
`--direction egress`, а для обоих направлений — `--direction both`. Перед
блокировкой проверьте список разрешённых адресов, NAT/CDN, порт, протокол и
независимый список угроз.

### 7. Применить CIDR или список угроз и уметь откатить

```sh
sudo bfban add 203.0.113.0/24
./scripts/fetch-threat-feed.sh --output=/tmp/feodo.txt
less /tmp/feodo.txt
sudo ./scripts/fetch-threat-feed.sh --apply
sudo bfban remove 203.0.113.10
sudo bfbandctl flush
```

Не блокируйте географию или ASN как замену проверенным признакам компрометации.
Для объёмной DDoS-атаки, которая заполняет канал, нужна фильтрация у
провайдера или очистка трафика: локальный сервер уже не может вернуть
пропускную способность канала.

## Как понять, откуда идёт DDoS

`bfban` сам по себе **не обнаруживает DDoS**. Он получает уже принятое решение
о блокировке. Источник атаки сначала нужно определить средствами наблюдения
за трафиком.

Быстрая последовательность:

```sh
# нагрузка на интерфейсы и ошибки
ip -s link
sar -n DEV 1
ethtool -S eth0

# состояние TCP/UDP и conntrack
ss -s
conntrack -S
nstat -az
```

Для поиска наиболее активных IPv4-источников во входящем трафике можно
использовать `tshark`:

```sh
sudo tshark -ni eth0 -a duration:30 -f 'ip' \
  -T fields -e ip.src 2>/dev/null |
  sort | uniq -c | sort -nr | head -50
```

Затем нужно проверить наиболее активные источники по независимым признакам:
порту назначения, флагам TCP, доле новых соединений, скорости и наличию в
известном списке угроз. Автоматически блокировать самый частый IP опасно: это может быть NAT,
прокси, CDN или легитимный клиент.

### Ограничение наблюдения при XDP

Если пакет отбрасывается в штатном режиме XDP драйвера, он может не дойти до обычного сетевого
стека и не попасть в `tcpdump`. Поэтому для расследования нужно либо временно
наблюдать трафик до включения XDP, либо иметь отдельную карту или кольцевой
буфер телеметрии, которые передают IP-адрес источника, протокол, порт и
счётчики. В текущей версии `bfban` такой телеметрии по источникам нет:
счётчики цепочки показывают количество совпадений, но не список наиболее
активных источников.

Для промышленного варианта в дальнейшем нужен отдельный `bfobserve` на eBPF:

```text
сетевой адаптер → карта наблюдения XDP → список источников в пользовательском
пространстве → решение администратора → список блокировки bfban
```

Это разделяет обнаружение атаки и применение блокировки и снижает риск
самоблокировки.

Методика по TCP-очередям, окнам, SYN-cookie и памяти описана в
[`docs/tcp-ddos-tuning.md`](docs/tcp-ddos-tuning.md). `bfban` не заменяет
настройку очереди TCP и фильтрацию у провайдера, если перегружен сам внешний
канал.

## Наблюдение трафика: `bfobserve`

`bfobserve` — режим наблюдения: он не блокирует адреса, а за короткий
промежуток времени собирает список наиболее активных источников и подсказывает
следующие действия. Текущая версия использует AF_PACKET и требует `root` или
`CAP_NET_RAW`; это наблюдатель в пользовательском пространстве, а не карта
телеметрии XDP.

Сначала посмотреть интерфейсы:

```sh
sudo bfobserve --list-interfaces
```

Пример вывода:

```text
Available interfaces:
  IFACE            STATE       MTU     COMMAND
  lo               up/running  65536   sudo bfobserve -i lo
  eth0             up/running  1500    sudo bfobserve -i eth0
  wg0              up           1420   sudo bfobserve -i wg0
```

Затем запустить наблюдение на WAN-интерфейсе:

```sh
sudo bfobserve --interface eth0 --seconds 30 --top 20
```

Отчёт показывает:

```text
#    SOURCE                                  PACKETS        BYTES        PPS        SYN        UDP    DPORT
1    198.51.100.20                             82000      61.2 MB       2733      81000          0       22
2    203.0.113.44                              47000      28.4 MB       1566          0      46000      443
```

Для automation/SIEM:

```sh
sudo bfobserve --interface eth0 --seconds 30 --top 100 --json
```

Для осторожных рекомендаций:

```sh
sudo bfobserve --interface eth0 --seconds 30 \
  --suggest --min-pps 1000
```

Команда только напечатает предложения вида:

```text
bfban add 198.51.100.20  # 2733 pps, 81000 SYN, 0 UDP
```

Администратор проверяет источник, список разрешённых адресов и список угроз,
после чего сам решает, выполнять ли `bfban add`. Это сделано намеренно:
автоматическая блокировка только по частоте может заблокировать NAT, CDN или
легитимного клиента.

## Тестовая матрица ядра и дистрибутивов

Для локальной регрессионной проверки выполните:

```sh
make test
```

Тестовая сборка включает отдельные механизмы имитации отказов и сохраняемый
фальшивый набор адресов ядра. При запуске с правами root проверяются отказы службы на
выбранной операции, ошибки сохранения до и после `rename()`, откат пакетной
операции, переход в режим сверки состояния, работа с CIDR, ограничение времени
чтения запроса и восстановление после перезапуска. Фальшивый набор сравнивается
с результатом `LIST` и файлом состояния. Прямой режим libbpfilter для этого теста
явно отключён; боевой путь проверяется отдельной сборкой с libbpfilter и
стендом из `docs/validation-lab.md`. Без прав root выполняются базовые проверки
CLI, а проверки Unix-сокета и отказов явно помечаются как `SKIP`, а не как
успешные.

Для первой версии зафиксирована такая проверочная база. Это не универсальное
утверждение о минимальной версии ядра самого `bfban`: совместимость зависит от
версии bpfilter, hook и конфигурации ядра.

| Компонент | Требование |
|---|---|
| Linux kernel | **6.6 или новее для целевой проверки** |
| libbpf | **1.2 или новее для прямого профиля** |
| BPF token mode | не требуется текущей реализацией |
| пользовательская часть | `clang`, `libbpf`, `bpftool`/BPF-файловая система по конфигурации системы |

Проверять нужно фактическое запущенное ядро, а не только версию дистрибутива:

```sh

```

### Почему именно eBPF/XDP

Научное и инженерное обоснование не в том, что любой eBPF-код быстрее
iptables. Возможный выигрыш возникает в конкретной точке обработки и при конкретном
профиле нагрузки. Академическая база — статья:

> Toke Høiland-Jørgensen, Jesper Dangaard Brouer, Daniel Borkmann, John
> Fastabend, Tom Herbert, David Ahern и David Miller. «The eXpress Data Path:
> Fast Programmable Packet Processing in the Operating System Kernel». ACM
> CoNEXT 2018. DOI: [10.1145/3281411.3281443](https://doi.org/10.1145/3281411.3281443).

1. XDP вызывается на раннем пути приёма пакета и может вернуть `XDP_DROP` до
   обычной обработки сетевым стеком.
2. Linux может JIT-компилировать eBPF в машинный код, но результат зависит от
   архитектуры и конфигурации ядра.
3. Точные адреса хранятся в хеш-таблицах, а CIDR проверяется по самому
   длинному совпадающему префиксу (LPM), без разворачивания сети в отдельные IP.
4. `chain update-set` в bpfilter атомарен и сохраняет счётчики, но сам bpfilter
   при этом заново создаёт BPF-программу с новым содержимым набора. Прямой API
   убирает fork/exec и разбор командной строки, но не делает обновление ядра
   бесплатным.

Это делает решение перспективным для раннего отбрасывания L3/L4-пакетов,
больших списков блокировки и высокой скорости пакетов. Это не доказывает
преимущество над современным nftables: nftables тоже поддерживает наборы,
динамические наборы, счётчики и ограничение скорости по источнику. Поэтому
обязательна контрольная серия измерений:

```text
legacy iptables  vs  nftables  vs  bpfilter Netfilter  vs  bpfilter XDP
```

Сравнивать нужно одинаковые правила и нагрузку: размер списка блокировки,
число пакетов в секунду, долю принятых и отброшенных пакетов, загрузку CPU,
задержку, IPv4/IPv6 и наличие счётчиков и журналирования.

Первичные источники описывают раннее выполнение XDP и live-frame режим в
[Linux kernel BPF documentation](https://docs.kernel.org/bpf/bpf_prog_run.html),
LPM в [Linux LPM-trie documentation](https://docs.kernel.org/bpf/map_lpm_trie.html),
а требования и поддержка конкретных точек подключения должны проверяться по API ядра,
который использует сам bpfilter.

## Как это интегрируется с Fail2ban

Fail2ban принимает решение, а `bfband` применяет его через клиент
`bfbandctl`:

```text
лог sshd/nginx/etc.
        │
        ▼
Fail2ban filter
        │ считает maxretry за findtime
        ▼
Fail2ban jail принимает решение о бане
        │
        ├── actionstart  → создать цепочку bpfilter и список блокировок
        ├── actionban    → bfbandctl add <ip>
        ├── actionunban  → bfbandctl remove <ip>
        └── actionstop   → удалить цепочку
```

`bfban` и `bfband` не читают логи и не знают, почему адрес был заблокирован.
Они получают от Fail2ban только команды. Например, при пяти неудачных
SSH-входах за десять минут action вызывает:

```sh
bfbandctl add 203.0.113.10
```

Когда заканчивается `bantime`, Fail2ban вызывает:

```sh
bfbandctl remove 203.0.113.10
```

`bfband` принимает эти команды через Unix-сокет. Затем он либо обновляет
набор через прямой C API `libbpfilter`, либо запускает запасной путь
`bfban` → `bfcli chain update-set`. Поэтому eBPF-программа остаётся
загруженной, а изменяется только содержимое соответствующего набора.
Fail2ban уже управляет временем жизни бана; отдельный TTL в MVP не нужен.

### Установка action

После сборки установить бинарник и action:

```sh
cd ~/bfban
make
sudo make install
```

Проверить, что доступны:

```text
/usr/sbin/bfban   # или PREFIX/sbin/bfban
/etc/fail2ban/action.d/bfban.conf
```

### Пример jail для SSH

Создать `/etc/fail2ban/jail.d/sshd-bfban.local`:

```ini
[sshd-bfban]
enabled = true
filter = sshd
backend = systemd
port = ssh
maxretry = 5
findtime = 10m
bantime = 1h
banaction = bfban
```

Затем перезапустить Fail2ban:

```sh
sudo systemctl restart fail2ban
sudo fail2ban-client status sshd-bfban
```

При старте jail action выполнит `bfbandctl init`. При бане и разбане IP будут
вызваны `actionban` и `actionunban` из
`/etc/fail2ban/action.d/bfban.conf`.

### Важное ограничение текущего MVP

Сейчас используется одна глобальная цепочка `bfban_input` и один файл состояния.
Поэтому безопасный вариант — один jail, например SSH. Если подключить
несколько jail одновременно, они будут использовать общий список, а
`actionstop` одного jail может очистить баны другого.

Текущий `bfband` всё ещё использует одну глобальную цепочку; отдельные
пространства имён для jail будут добавлены позже. Поэтому до их появления следует
использовать один общий jail/action, либо не включать `actionstop` на
отдельных jail.

### Проверка работы

Состояние Fail2ban:

```sh
sudo fail2ban-client status sshd-bfban
```

Список адресов, переданных в bpfilter:

```sh
sudo bfban list
```

Состояние цепочки bpfilter:

```sh
sudo bfcli chain get --name bfban_input
```

В счётчиках цепочки можно увидеть, сколько пакетов было отброшено. Для
диагностики сначала рекомендуется использовать `bantime = 10m`, проверить
цепочку вручную и только затем включать длительные баны.

## Ограничения: чего `bfban` не делает

`bfban` не является полной защитой от объёмной DDoS-атаки. Если канал уже
забит, локальный сервер Linux не сможет устранить проблему — нужна фильтрация
или очистка трафика у провайдера.

`bfban` также не заменяет полноценный межсетевой экран с отслеживанием
состояния соединений. NAT, conntrack,
маршрутизация и постоянные правила должны оставаться в nftables/iptables или
другом основном межсетевом экране.

Для ограничения скорости по источнику потребуется отдельная реализация
алгоритма token bucket и состояния в картах BPF. В текущей версии этого нет.

## Использование памяти

Использование памяти состоит из трёх основных частей:

1. Процесс `bfband` хранит таблицу адресов и сроки блокировки в своей памяти.
   При текущем лимите `65536` записей это примерно **4.5 MiB** для таблицы,
   не считая обычных накладных расходов процесса.
2. `bfcli` и `libbpfilter` временно используют дополнительную память при
   загрузке или обновлении цепочки.
3. Карты BPF живут в памяти ядра. Для точной оценки нужно смотреть
   `bpftool map show` и `bpftool map dump`; расход зависит от типа карты, размера
   ключа, числа элементов и накладных расходов распределителя памяти ядра.

Грубая инженерная оценка для списка блокировки — десятки байт памяти ядра на IPv4
адрес и больше для IPv6/LPM. Демон использует bounded open-addressing index для
быстрого поиска ADD/DEL/TTL; таблица адресов остаётся ограниченной. То есть
`100000` адресов обычно означают единицы мегабайт, а не сотни мегабайт, но
это нужно подтвердить измерением на целевом ядре. Таблица уже размещается в
динамической памяти и ограничена лимитом `65536` записей; для промышленной
эксплуатации нужны измерения на целевом ядре и наблюдение за фактическим
размером карты BPF.

## CIDR и сети

Без CIDR полноценный загрузчик списков угроз неполон. Важно, что bpfilter уже
поддерживает `ip4.snet`, `ip6.snet` и наборы LPM. Поэтому для списка блокировки
нужно разделять четыре набора:

```text
banlist4      — точные IPv4
banlist4net   — IPv4 CIDR
banlist6      — точные IPv6
banlist6net   — IPv6 CIDR
```

`bfban` теперь принимает как `203.0.113.10`, так и `203.0.113.0/24`, а при
инициализации цепочки создаёт соответствующие наборы точных адресов и LPM.

## Проверка на списках угроз

Список угроз — это не база всех ботов. Обычно это опубликованный и проверенный
список сетевых индикаторов: IP-адресов или CIDR-сетей, связанных с конкретной
угрозой — например, с управляющей инфраструктурой ботнета или известным
вредоносным хостингом. Такие списки необязательны: `bfban` сам их не ищет, не
оценивает репутацию адресов и не доказывает, что адрес всё ещё вредоносен.

Скрипт [`scripts/fetch-threat-feed.sh`](scripts/fetch-threat-feed.sh) по
умолчанию использует рекомендованный IPv4-список Feodo Tracker, проверяет его
формат и ничего не блокирует без явного `--apply`. Это воспроизводимый пример
специализированного списка управляющих узлов ботнета, а не универсальный
blocklist. Spamhaus DROP — отдельный источник CIDR-сетей; для него нужен свой
загрузчик и соблюдение условий использования источника.

Не превращайте список стран, ASN или непроверенный reputation dump в правило
блокировки: общие хостинги, NAT, VPN и CDN создают много ложных срабатываний.

```sh
./scripts/fetch-threat-feed.sh --output=/tmp/feodo.txt
less /tmp/feodo.txt
sudo ./scripts/fetch-threat-feed.sh --apply
```

Feodo Tracker описывает адреса как подтверждённые управляющие узлы ботнета и
предупреждает, что расширенный исторический список имеет более высокий риск
ложных срабатываний:
<https://feodotracker.abuse.ch/blocklist/>.
Spamhaus DROP можно использовать для отдельного загрузчика с поддержкой CIDR, но его
обновление должно быть автоматическим и не чаще разрешённой частоты:
<https://www.spamhaus.org/faqs/do-not-route-or-peer-drop/>.

Эти списки предназначены для защитной проверки и подключения к списку
блокировки, а не для активного сканирования или атак на перечисленные адреса.

## Демон `bfband`

Демон `bfband`:

- слушает Unix-сокет `/run/bfban/bfban.sock`;
- принимает `ADD`, `DEL`, `LIST`, `FLUSH`;
- поддерживает TTL для банов;
- восстанавливает состояние после перезапуска;
- сохраняет изменения наборов;
- принимает команды через один Unix-сокет;
- ограничивает доступ правами Unix и политикой root и группы.

Текущий текстовый API:

```text
ADD 203.0.113.10 3600
DEL 203.0.113.10
ADD_MANY 203.0.113.10 198.51.100.0/24
LIST
FLUSH
```

Fail2ban вызывает только небольшой action-клиент `bfbandctl`, а не управляет
объектами eBPF самостоятельно.

Запуск после установки:

```sh
sudo systemctl enable --now bfband
sudo bfbandctl ping
```

Если доступен `libbpfilter`, `ADD_MANY` группирует точные и CIDR-записи по
семейству адресов и обновляет набор через прямой C API. Без библиотеки сохраняется
совместимый fallback через `bfban`/`bfcli`.

Перед сообщением об успешной записи демон выполняет `fsync` файла и пытается
выполнить `fsync` каталога.
Изменение ядра и переименование файла состояния не образуют одну физическую
транзакцию, поэтому при ошибке сохранения выполняется попытка отката в ядре,
а при запуске демона записанное состояние можно применить повторно. Если
компенсирующий откат не удался, демон сообщает об этом и не принимает новые
изменения до успешного явного `INIT`.

Команда Fail2ban `actioncheck` проверяет доступность Unix-сокета демона. Это не
проверка каждой точки обработки пакетов и не тест производительности пути
обработки; восстановление выполняют `bfbandctl init` и сверка состояния демона.

## Поиск источника нагрузки

`bfobserve` — наблюдатель трафика для ответа на практический вопрос «откуда
идёт нагрузка?». Он за короткое окно показывает самые активные источники, PPS,
байты, SYN, UDP и последний порт назначения, а `--suggest` печатает готовые команды
для передачи подозрительных адресов в `bfban`.

Сначала администратор выбирает интерфейс понятным списком:

```sh
sudo bfobserve --list-interfaces
sudo bfobserve --interface eth0 --seconds 30 --top 20
sudo bfobserve --interface eth0 --seconds 30 --top 20 --suggest --min-pps 100
sudo bfobserve --interface eth0 --seconds 30 --json
```

Пример вывода интерфейсов:

```text
Available interfaces:
  IFACE            STATE       MTU     COMMAND
  lo               up/running  65536   sudo bfobserve -i lo
  eth0             up/running  1500    sudo bfobserve -i eth0
```

Это именно диагностический слой: он не блокирует адрес автоматически и не
выдаёт «ботнет» по одному признаку. Администратор видит источник, проверяет
порт/протокол и затем применяет адрес через `bfban`, Fail2ban или отдельную
политику. Нужны `root` или `CAP_NET_RAW`; текущая версия использует безопасный
захват AF_PACKET, поэтому это не обещание, что вся объёмная атака будет видна
после аппаратной обработки или фильтрации у провайдера.

## Итог: когда использовать `bfban`

Проект имеет смысл как:

- средство применения решений Fail2ban/CrowdSec;
- динамический список блокировок на пограничном сервере Linux;
- раннее отбрасывание пакетов через XDP, если это поддерживает интерфейс;
- специализированная фильтрация, которую неудобно выражать обычными
  правилами межсетевого экрана.

Для небольшого сервера с несколькими десятками правил обычный nftables
обычно проще. Современный nftables также поддерживает наборы, сроки действия и
ограничение скорости по источнику, поэтому преимущество `bfban` нужно подтверждать
измерениями, а не предполагать заранее.
